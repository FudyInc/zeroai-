## Lo que pido

Cuatro trabajos. Ninguno bloquea nada hoy; el orden es mi sugerencia, contrástala.

### 1 · core — que el aborto de la tanda avise (F1)

`scripts/tanda.py:403` hace `return 2` cuando la puerta de aislamiento encuentra
intrusos, **antes** del `notify_owner` que está en la línea 437 y solo corre en el camino
de éxito. Resultado medido: la tanda avisa por WhatsApp cuando funciona y calla cuando
está muerta.

Eso es lo que hizo que ocho días de parálisis pasaran inadvertidos:

```
$ journalctl --user -u zero-dia.service --since <cualquiera de esos días> | grep -ci aviso
0
```

Es una guarda de seguridad, así que el cambio lo mira una persona — por eso va por acá y
no encolado directo. Alcance sugerido: avisar antes del `return 2`, y de paso separar en
`planificar.py` el caso "no propuso tareas" del caso "no pudo correr" (el 2026-08-30 falló
por OAuth caducado y la salida se veía idéntica a un día sin trabajo pendiente).

### 2 · core — un commit por día en `audit/diaria`, no uno por corrida (M1)

`scripts/commitear-auditoria.sh:48` tiene una guarda para no crear commits vacíos:

```bash
if [ "$TREE" = "$(git rev-parse "$BASE^{tree}")" ]; then
  echo "  sin cambios respecto a $RAMA — no se crea commit"
```

**No puede dispararse nunca**: el JSON lleva `cuando` (timestamp) y `segundos` por check,
así que el árbol siempre difiere. El 2026-09-04 quedaron dos commits con mensaje idéntico
para la misma fecha, cuyo único diff era `20.3` → `20.5`.

Arreglo: comparar los campos que importan (`hallazgos`, o los `checks` sin `segundos`), o
hacer `--amend` cuando ya hay commit para esa fecha.

Detalle del mismo archivo, sin prisa: `BASE` (línea 35) cae siempre en la rama misma tras
el primer día, así que el árbol de `audit/diaria` queda congelado en el `main` del día 1
para siempre. Una rama huérfana haría lo mismo sin arrastrar el repo entero.

### 3 · core — tests para los dos módulos que escriben en la nube (A5)

```
$ grep -rl cloud_env tests/      → 0
$ grep -rl crm_supabase tests/   → 0
```

`zero/cloud_env.py` (66 líneas) y `zero/crm_supabase.py` (160) son los únicos módulos sin
ninguna cobertura que escriben fuera del disco local. Un error ahí no se revierte con
`git checkout`.

Ojo: el planificador ya descartó esto dos veces con buen criterio ("los tests se agregan
cuando hay cambio de lógica, no para llenar cupo"). Lo pido igual porque el argumento no
es cobertura por cobertura, es que **son los que tocan producción**. Si al escribir el
prompt te convence más el criterio del planificador que el mío, dilo y lo bajo.
